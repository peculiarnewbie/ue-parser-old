# Legacy UAsset class coverage

> Historical document. This scoreboard describes the repository's former asset
> parser surface and is retained for provenance only; UTrace is the current
> product scope. Do not use this file to plan new parser work.

The living scoreboard for which UObject export classes the parser can decode, and
how completely. This is the prioritization surface — when we pick up new asset
work, we pick from the **Not yet supported** table and move it up.

Compatibility target: **uncooked editor packages** (UE 5.7.2), versioned tagged
properties. This matters a lot for mesh/texture work: in uncooked editor assets
the heavy payload is *editor bulk data* (`FTextureSource`, `FMeshDescription`,
`FSkeletalMeshModel`) serialized **after** the tagged-property stream, not the
cooked render-data path. See [per-class notes](#per-class-notes).

## How decoding works (two layers)

1. **Generic, class-agnostic** (`package.rs`): summary, name map, import/export
   maps, `FPackageIndex` resolution, soft-object paths, and the
   **tagged-property stream** (the `NAME_None`-terminated `UPROPERTY` block).
   Works on *any* `.uasset`.
2. **Class-specific decoders** (`asset.rs`, dispatched in `decode_export`): parse
   the bespoke binary **tail** that follows the property stream.

The catch: the generic fallback (`UObjectDecoder`) accepts *any* class but only
reads the property stream plus a tiny footer (4-byte zero or 20-byte object
GUID). **If a class has any other binary tail, it hard-errors** with
`MalformedData: left N trailing bytes` (`consume_uobject_export_footer`,
`asset.rs:1214`). So a class is only "properties-only" today if it happens to
have *no* tail; everything with a tail currently fails outright.

## Measured coverage (the real project)

Generated by `cargo run --release --example catalog -- <root>` (see
`examples/catalog.rs`). It walks a tree, parses each `.uasset`/`.umap`, and for
each file's primary export records the class **and the decode outcome**
(decoded / failed / skipped), with a sample failure message per class. Re-run it
after format work to watch coverage move.

Last run (2026-06-30) against the actual game project
`Arif_MBPrototype/Content/Mana`:

- **6 625** files, **6 625 parsed OK (0 package failures)**. Of the parsed
  primaries: **1 892 decode**, the rest fail at the decode layer (binary tails).
- A prior run showed 791 package-layer failures (~12%), all from a single bug: the

### What already works (~1 120 files)

The generic `UObjectDecoder` already fully decodes every primary export whose
class has **no binary tail** — i.e. pure tagged-property objects. In this project
that is a big, useful slice:

- **Custom Mana gameplay data**: `M_Line` (124), `M_LipsyncAsset` (112),
  `M_InputMappingContext` (30), `M_ShopConfig` (20), `M_ShopListingEntry` (17),
  `M_CameraConfig` (12), `M_LocomotionConfig` (10), `M_LootTable` (10), and the
  long tail of one-off `M_*Config` assets — all 100% decoded.
- **Engine property-only assets**: `MaterialFunction` (148), `Blueprint` (63),
  `WidgetBlueprint` (55), `InputAction` (83), `BlackboardData` (9),
  `PhysicalMaterial` (19), `CurveFloat` (14).
- **Already-supported structured types**: `DataTable` (183/185),
  `StringTable` (23), `CompositeDataTable` (3).

### Why the rest fails — three buckets

Decode failures (5 088) sort into three root causes, from the catalog's sampled
messages:

1. **`left N trailing bytes`** — the dominant bucket. Property stream parses
   clean; a class-specific binary tail follows. Covers `AnimSequence`,
   `Texture2D`, `MaterialInstanceConstant`, `M_VisemeTimelineData`, `Material`,
   `StaticMesh`, `SkeletalMesh` (3.7 MB tail!), `CustomizableObject`,
   `*GeneratedClass`, `NiagaraSystem`, `PhysicsAsset`, `Font`/`FontFace`, etc.
2. **`expected export footer object-guid marker 1 … got 0`** — the footer
   heuristic in `consume_uobject_export_footer` false-positives: it sees a 4- or
   20-byte remainder and assumes a GUID/zero footer, but those bytes are actually
   tail data. Covers `AnimMontage`, `BlendSpace`, `BlendSpace1D`, `PoseAsset`.
3. **Genuine mid-stream property bugs** — small but real. e.g.
   `M_HitStrengthAnimationData` fails reading a soft-object `SubPath` inside a Map
   (`Entries[0].Value.SubPath.Data` over-reads), and some textures hit a name
   index out of range inside an `InterchangeAssetImportData` subobject. These are
   correctness bugs in the property decoder, not tail issues — see
   `memory/softobject-property-misdecode.md`.

## Status update (2026-07-01): Skeleton done

`USkeleton` now has a dedicated `SkeletonDecoder`. Unlike Texture/StaticMesh, the
bone hierarchy is **not** in the property stream — it's the `FReferenceSkeleton` at
the start of the export tail (`USkeleton::Serialize` runs `Super::Serialize` then
`Ar << ReferenceSkeleton`). The decoder reads the property stream, consumes the
object-guid footer, then parses the bone-info `TArray`: per bone `FName Name`,
`i32 ParentIndex`, and an editor-only `FString ExportName` (the FTransform pose
array and the rest of the tail are left unparsed). Output: `kind: "Skeleton"` with
a `bones` array (name + parent_index); schema bumped to **6**. Bone count = array
length; sockets come from the separate `SkeletalMeshSocket` exports; preview mesh is
a soft-object property. Verified: 25/25 project skeletons decode with valid
single-root hierarchies (e.g. `root`→`pelvis`→`spine_01`, 364 bones). Tests:
`skeleton_decoder_parses_reference_skeleton_bones`.

`SkeletalMesh` (the mesh, not the skeleton) is still generic-UObject + raw tail —
its `FReferenceSkeleton` lives inside `FSkeletalMeshModel` deeper in the tail; a
follow-up if its bone list is wanted directly.

## Status update (2026-07-01): Texture2D done

Texture2D is **done** at the metadata bar — all via the property stream, no bespoke
decoder. Required one general fix: **enum-backed `ByteProperty` decodes as its
entry `FName`** (it serializes as an 8-byte FName, not a u8; we read 1 byte before).
That unblocks `Format`, `CompressionSettings`, `LODGroup`, and enum byte properties
across *every* asset. Decoded for a real texture: `Source.SizeX/SizeY=512`,
`NumMips=1`, `Source.Format=TSF_BGRA8`, `CompressionSettings=TC_Masks`,
`LODGroup=TEXTUREGROUP_Character`, `SRGB=false`. Dimensions/mips/slices come from
the `Source` (`FTextureSource`) struct, which already decodes; the struct/array
property output already recurses, so these surface in JSON. Tests:
`decodes_enum_backed_byte_property_as_name`, `decodes_plain_byte_property_as_uint`.

## Status update (2026-07-01): raw-tail fallback landed

The raw-tail fallback (priority 0) is **done**. `UObjectDecoder` now retains
unrecognized trailing bytes as a raw `Span` instead of erroring, and the export
footer is consumed leniently (only a canonical zero/guid footer is parsed; any
other remainder becomes the tail). The CLI surfaces `tail_bytes` on UObject assets
(schema bumped to **4**).

Impact on `MBPrototype/Content/Mana`: primary exports decoded **1 120 → 7 695**
(of 7 758; ~99%), failures **5 866 → 63**.

**StaticMesh (priority 3): the export decodes.** Its metadata is all in the
tagged-property stream — `StaticMaterials` (slot names + material refs),
`SourceModels` (LOD count = array length), `ExtendedBounds`, lightmap settings —
plus a ~94-byte retained tail. No bespoke tail parser was needed; the heavy mesh
data lives in a separate bulk segment, not the export.

**Import-data sub-object bug — FIXED 2026-07-01.** `UAssetImportData::Serialize`
writes a JSON `FString` *before* its parent's property stream (uncooked packages),
so every `*ImportData` sub-object (`FbxStaticMeshImportData`,
`InterchangeAssetImportData`, …) had its stream start misread. `decode_uobject_properties`
now consumes that leading JSON blob for import-data classes when editor data is
present. Single root cause; one fix.

Result: **StaticMesh whole-file `inspect` 41% → 98% (117/120 sampled)**; the 3
stragglers are legacy assets in the pre-UE5.4 "complete type name" property format
(genuine `UnsupportedVersion`, not a bug). **Textures: 20/20 sampled inspect clean**
(same fix). StaticMesh is **done** at the metadata+properties bar.

**Per-export resilient inspect — DONE 2026-07-01.** `uasset inspect` no longer
aborts a whole file on one bad export: it emits all decoded assets, lists failures
in a `decode_errors` array, sets `status: "partial"`, and exits `6` (distinct from
the hard-error codes). Schema bumped to **5**. So legacy/edge exports degrade
gracefully instead of blanking the asset.

Still open: the ~63 remaining primary failures are other bucket-3 property
misparses to chase per-class (now surfaced as `decode_errors` rather than aborting).

## Enabling prerequisite: raw-tail fallback (unblocks buckets 1 & 2) — DONE

Make `UObjectDecoder` **retain unrecognized trailing bytes as a raw `Span`
instead of erroring**, and stop the footer heuristic from treating an arbitrary
4/20-byte remainder as a footer (only consume a footer that actually validates;
otherwise hand the bytes to the raw tail). This single change flips buckets 1 and
2 — the large majority of the 5 088 failures — from 🟥 to 🟡 (properties decoded
+ raw tail surfaced) in one move, and gives each future class decoder a known byte
range to crack. Bucket 3 is separate property-decoder bug-fixing.

## Per-class notes

### AnimSequence / AnimMontage (Pri 1)
The dominant asset type in this project (~2500 incl. montages/blendspaces).
`UAnimSequence::Serialize` / `UAnimMontage::Serialize`. Props carry the skeleton
ref, rate scale, montage sections/slots/notifies, and blend settings. The tail
holds raw/compressed track data (`FRawAnimSequenceTrack`, `FCompressedAnimSequence`)
— bulk, skip — but its header gives frame count, sequence length, and track/curve
names, which is the metadata worth extracting. Montages/blendspaces currently trip
the *footer-marker* failure bucket, so they need the raw-tail fallback before any
class-specific decode. Source: `Engine/Private/Animation/AnimSequence.cpp`,
`AnimMontage.cpp`, `AnimationRuntime`.

### Texture2D (Pri 2)
`UTexture::Serialize` / `UTexture2D::Serialize`. Editor-uncooked stores source
art in `FTextureSource` (UE `Engine/Classes/Engine/TextureDefines.h`,
`Engine/Private/TextureDerivedData.cpp`). Extractable metadata without touching
pixel bulk data: `SizeX`, `SizeY`, `NumSlices`, `NumMips`, `ETextureSourceFormat`,
`bPNGCompressed`/compression format. Most user-facing settings
(CompressionSettings, SRGB, Filter, AddressX/Y, LODGroup, MipGenSettings) are
already in the tagged-property stream.

### StaticMesh (Pri 3)
`UStaticMesh::Serialize` writes `bool bCooked`, then in editor the per-LOD
`FMeshDescriptionBulkData` / legacy `FStaticMeshSourceModel`. Tagged props carry
`StaticMaterials` (slot name + material ref + UV data) and `LODGroup`.
Metadata target: LOD count, material slot names, bounds, per-LOD vertex/triangle
counts. Geometry buffers themselves are bulk data — out of scope for "metadata."

### SkeletalMesh / Skeleton (Pri 4)
`USkeletalMesh::Serialize` → `FReferenceSkeleton` (bone name/parent/ref-pose
arrays) and editor `FSkeletalMeshModel`. `USkeleton` separately owns the
authoritative `FReferenceSkeleton` + bone tree + virtual bones + sockets.
Metadata target: bone count and hierarchy, material slots, LOD count, socket
names. Render/skin-weight buffers are bulk data — out of scope.
